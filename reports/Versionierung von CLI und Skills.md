# Eine Vertragsnummer entkoppelt CLI und Skills

shade-kit sollte den Lockstep aufgeben und die Kompatibilität zwischen Skills und CLI über eine **eigene, ganzzahlige CLI-Vertragsversion mit Fenster** prüfen. Die Engine erklärt `Current` und `MinSupported`, jeder Skill nennt im Handshake die eine Vertragsnummer, für die er geschrieben ist, und die Engine akzeptiert, wenn `MinSupported ≤ R ≤ Current` gilt. Damit setzt die Empfehlung die gefragte Option „unabhängige Versionen mit gegenseitigen Mindestversionen“ um, aber auf einer Vertragsachse statt auf der Achse der Produkt-SemVer. Die Produktversion der CLI bleibt bei GitVersion. Die Skills brauchen überhaupt keine eigene Produktversion mehr, denn kein Agent liest `metadata.version` aus; nur der eigene Guard-Test tut das. Verteilt wird weiter wie heute über den Tag `v<engine>` oder `main`. Ein gewöhnliches Release kommt damit ganz ohne Versionsänderung in den Skills aus. Nur eine Änderung an der für Skills sichtbaren CLI-Oberfläche verlangt noch Handarbeit: eine Konstante und sieben gleichlautende Handshake-Zeilen, und ein Snapshot-Test erzwingt sie. Der größte Gewinn liegt beim lokalen Testen: Jeder Build desselben Codes trägt dieselbe Vertragsnummer, also prüft der Handshake Feature-Branch-Builds wirklich, statt sie wie heute als Prerelease durchzuwinken. Am besten erfolgt der Umbau vor dem ersten installierbaren Release-Tag. Bis dahin gibt es im Feld keine Engine, die die neue Option still ignorieren würde.

## Heute trägt eine Zahl zwei Bedeutungen, und beide Mechanismen widersprechen sich

Im Repository gibt es genau eine berechnete Version. GitVersion leitet sie aus der Git-Historie und aus `next-version: v0.9.0` ab, sie wird als Informational Version eingebettet und zur Laufzeit von `EngineVersionProvider` gelesen (**FACT**, [GitVersion.yml](../GitVersion.yml), [EngineVersionProvider.cs](../src/CreativeCoders.ShadeKit.Core/Engine/EngineVersionProvider.cs)). Daneben führen die Skills eine zweite, von Hand gepflegte Kopie. **Alle 19 `SKILL.md` tragen `version: 0.9.0` im Frontmatter. Fünf Skills führen den Handshake aus, und zwei Befehlslisten wiederholen ihn. Zusammen sind das 26 Zeilen in 19 Dateien**, die bei einer Anhebung gemeinsam geändert werden müssen (**FACT**, `git grep -c 0.9.0 -- skills`). Die Kopie im Fließtext ist nötig, weil Claude Code das Frontmatter vor dem Modell verbirgt (beobachtet mit 2.1.318) und Copilot CLI es seit 1.0.48 ebenfalls entfernt ([Copilot CLI changelog](https://github.com/github/copilot-cli/blob/main/changelog.md)). Codex lässt das Modell zwar die rohe Datei lesen, wertet aber nur `name`, `description` und `metadata.short-description` aus ([openai/codex parser.rs](https://github.com/openai/codex/blob/main/codex-rs/skills/src/parser.rs)).

`SkillKitVersionTests` koppelt beide Kopien an die GitVersion-Version **des Builds, der den Test ausführt** (`new EngineVersionProvider().Version`). Das Ergebnis hängt deshalb von Branch, lokal vorhandenen Tags und `next-version` ab, nicht nur von den eingecheckten Dateien (**FACT**, [SkillKitVersionTests.cs](../tests/CreativeCoders.ShadeKit.Core.Tests/Skills/SkillKitVersionTests.cs)). Zur Laufzeit gilt die entgegengesetzte Logik. Weicht major.minor ab, endet `version --expect` mit Exit 50, aber **eine Prerelease-Engine warnt nur** ([EngineVersionChecker.cs](../src/CreativeCoders.ShadeKit.Core/Versions/EngineVersionChecker.cs)). Auf diesem Branch lautet die Engine-Version `0.9.0-rework-versioning-branch-mgmt.4`, und `--expect 0.8.0` wie `--expect 1.0.0` liefern `ok:true` (**FACT**, ausgeführt am 2026-11-21). Auf jedem Feature-Branch ist der Handshake damit faktisch abgeschaltet, während der Guard dort weiter auf exakter major.minor-Gleichheit besteht. Lokal wird der Ablehnungspfad nie geprüft. Dazu installiert eine Branch-Engine ohne `SHADE_KIT_MARKETPLACE_SOURCE` die Skills von GitHub `main`, also weder die Skills des Branches noch die, gegen die die Engine getestet wurde ([IntegrationService.cs](../src/CreativeCoders.ShadeKit.Core/Integrations/IntegrationService.cs)).

Die Historie zeigt, wie teuer die Kopplung ist. Von den drei Anhebungen (0.7 → 0.8 → 0.9) waren **zwei reaktiv erzwungen**. Die erste kam, weil der neue Guard nach dem Tag `v0.8.0` fehlschlug. Die zweite kam, weil `shade-kit-new` die Option `feature new --move-source` brauchte, die 0.8-Engines nicht kennen ([06-2](../docs/feature-packages/06-2-skill-conventions-and-version.md), [09-Implementierung](../docs/implementation/09-discuss-and-intake.md)). Daran zeigt sich der Kern des Problems. Der Handshake kann „braucht Engine ≥ 0.9.1“ nicht ausdrücken, weil der Patch ignoriert wird. Deshalb erzwingt jede Abhängigkeit eines Skills von der Engine eine kitweite Minor-Anhebung über mehr als 20 Dateien plus `GitVersion.yml`, auch wenn 18 von 19 Skills unverändert sind. Umgekehrt zwingt eine reine Engine-Minor-Anhebung, alle Skills neu zu schreiben, obwohl sich kein Skill-Text geändert hat. Die eigene Dokumentation nennt den Widerspruch: Die Handanhebung „still breaks the rule in `GitVersion.yml` that no version is maintained by hand“ ([06-2](../docs/feature-packages/06-2-skill-conventions-and-version.md)). Eine Zahl soll gleichzeitig sagen, welcher Produkt-Build das ist (ändert sich mit jedem Commit, gehört GitVersion), und auf welchen CLI-Vertrag sich die Skills verlassen (sollte sich selten ändern, gehört den Autoren). Diese doppelte Bedeutung ist die eigentliche Ursache.

## Fünf Optionen gegen die harten Grenzen des Repos

Fünf Randbedingungen begrenzen jede Lösung. Für alle drei Agenten gibt es eine einzige Skill-Quelle ohne agentenspezifische Manifeste, abgesichert durch `SingleSkillSourceTests`. Es gibt keine Transformation beim Installieren. Das Plugin wird direkt aus dem Git-Baum am Tag oder an `main` installiert. Das Modell sieht das Frontmatter in Claude Code und Copilot nicht. Und der Parser ignoriert unbekannte Optionen still: `--expect=1.2.3` endet mit Exit 0 ohne Prüfung (**FACT**, [06-1](../docs/feature-packages/06-1-engine-version-check.md)). Die letzte Bedingung ist die am wenigsten offensichtliche und wird bei der Bewertung entscheidend.

| Option | Änderungen pro normalem Release | Änderungen bei neuer, für Skills sichtbarer CLI-Funktion | Guard an GitVersion gekoppelt | Check auf Dev-Builds sinnvoll | Agentenneutral | Umbau der Integrationen |
|---|---|---|---|---|---|---|
| (a) Lockstep, automatisch gestempelt | 0–1 (Release-PR mergen) | kitweite Minor-Anhebung | ja | nein | ja | keiner |
| (b) Version aus mitgelieferter Datei | 1 Datei | kitweite Minor-Anhebung | ja | nein | **nein** (Pfad je Agent) | keiner |
| (c) Unabhängige Produkt-SemVer mit gegenseitigen Mindestversionen | 0 | Minimum anheben (leicht vergessen) | nein | **nein** (SemVer-Prerelease-Ordnung) | ja | **groß** |
| (d) Vertragsversion mit Fenster | **0** | 1 Konstante + 7 Zeilen, testgestützt | **nein** | **ja** | ja | keiner |
| (e) Reine Capability-Abfrage | 0 | Prüflogik in jedem Skill | nein | ja | ja | keiner |

**(a) Automatisierter Lockstep** spart Tipparbeit, beseitigt aber keine Kopplung. Am besten passt hier release-please im Manifest-Modus. Es ist das einzige untersuchte Werkzeug, das vor dem Tag per Release-PR Versionen in beliebige Textdateien schreibt ([release-please manifest-releaser](https://raw.githubusercontent.com/googleapis/release-please/main/docs/manifest-releaser.md)). Sein Generic-Updater braucht allerdings Marker auf den Versionszeilen ([generic.ts](https://raw.githubusercontent.com/googleapis/release-please/main/src/updaters/generic.ts)). Ein Marker wie `version: 0.9.0 # x-release-please-version` bricht die Regex des Guards, der den Kommentar als Teil des Werts liest (**FACT**). Außerdem lösen Tags, die mit dem Standard-`GITHUB_TOKEN` erzeugt werden, vermutlich keine weiteren Workflows aus (**unverifiziert**). GitVersion, MinVer und Nerdbank.GitVersioning berechnen Versionen nur und schreiben nie in Markdown ([GitVersion 7.0 configuration](https://gitversion.net/7.0/docs/reference/configuration), [MinVer README](https://raw.githubusercontent.com/adamralph/minver/main/README.md), [NBGV version.json](https://dotnet.github.io/Nerdbank.GitVersioning/docs/versionJson.html)). Die Option lässt die Prerelease-Lücke, den Branch-installiert-`main`-Effekt und die fehlende Patch-Abhängigkeit unberührt.

**(b) Version aus einer mitgelieferten Datei** scheitert an der Agentenneutralität. Claude Code ersetzt `${CLAUDE_SKILL_DIR}` und `${CLAUDE_PLUGIN_ROOT}` im Skill-Text und kann mit `` !`…` `` sogar vorab Befehle ausführen ([Claude Code skills docs](https://code.claude.com/docs/en/skills)). Ein fehlgeschlagener `` !`…` ``-Befehl bricht aber den ganzen Skill ab, also auch die Erklärung eines Exit 50. Copilot dokumentiert keine Ersetzung im `SKILL.md`, dort käme der Platzhalter wörtlich an ([Copilot CLI plugin reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference)). Ob Copilot dem Modell einen absoluten Skill-Pfad nennt, ist **unverifiziert**. Codex nennt ihn nachweislich ([catalog_prompt.rs](https://github.com/openai/codex/blob/main/codex-rs/ext/skills/src/catalog_prompt.rs)). Ein `version` in `plugin.json` scheidet ebenfalls aus. Kein Agent gibt den Wert an das Modell weiter, und in Claude Code **friert er Nutzer auf dem Cache ein, bis sich der String ändert**. Das würde die SHA-basierten Updates auf dem `main`-Fallback stoppen ([Claude Code plugin loading](https://code.claude.com/docs/en/plugins/loading.md)). Die Variante, in der die Engine das Frontmatter über `--skill-dir` selbst liest, senkt nur die Zahl der Stellen und lässt die Kopplung bestehen.

**(c) Unabhängige Produktversionen mit beidseitigen Mindestversionen** prüft der Bericht ausdrücklich, und die Idee ist richtig. In der Ausführung über Produkt-SemVer scheitert sie aber an drei Punkten. Erstens steht die Ableitung des Marketplace-Refs `v<engine>` auf dem Lockstep. Getrennte Ströme verlangen getrennte Tags (etwa `skills-v*`), ein Mapping „Engine-Version → passender Skills-Tag“, eine Tag-Liste statt eines `git ls-remote` pro Tag sowie Umbauten in `MarketplaceSource`, in allen drei `*Integration.cs` und in `release.yml`. Das ist laut Bestandsaufnahme die invasivste Variante. Zweitens fällt eine Mindestversion auf Produkt-SemVer genau beim lokalen Testen um: **Prereleases haben laut SemVer eine niedrigere Präzedenz als die zugehörige Release-Version** ([SemVer 2.0.0](https://semver.org/)). Ein Branch-Build `0.10.0-feature.4` erfüllt daher `>= 0.10.0` nicht. Terraform umgeht das, indem es Prereleases in Bereichen gar nicht matcht ([Terraform Version Constraints](https://developer.hashicorp.com/terraform/language/expressions/version-constraints)). Drittens ändern sich Produktversionen mit jedem Release. Ein daran gebundenes Minimum ist also verrauscht und wird leicht vergessen. Hinzu kommt, dass eine Skills-SemVer keinen Abnehmer hat. Claude Code versioniert das Plugin über den Commit-SHA, Codex über den festen Wert `local` ([openai/codex store.rs](https://github.com/openai/codex/blob/main/codex-rs/core-plugins/src/store.rs)), und `metadata.version` liest nur der eigene Guard.

**(d) Eine eigene Vertragsversion** ist das Muster, auf das reife Host-Plugin-Systeme setzen. Das Terraform-Plugin-Protokoll v5/v6 ist unabhängig von der CLI-Version ([Terraform Plugin Protocol](https://developer.hashicorp.com/terraform/plugin/terraform-plugin-protocol)). Bei der Docker Engine API kennt der Daemon ein konfigurierbares Minimum und lehnt ältere Clients mit „client version 1.43 is too old. Minimum supported API version is 1.44“ ab ([Docker blog: Engine v29](https://www.docker.com/blog/docker-engine-version-29/)). MCP trennt `protocolVersion` von `serverInfo.version` ([MCP Lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)). Im eigenen Repo existiert die Vorlage schon: ganzzahlige Formatversionen pro Datei, die sich „only when the structure changes, not with every engine release“ ändern, mit `minEngineVersion` und `formats` in `version --json` ([FormatRegistry.cs](../src/CreativeCoders.ShadeKit.Core/Formats/FormatRegistry.cs)). **(e) Reine Capability-Abfrage** nach LSP-Art ([LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)) würde Versionsnummern ganz abschaffen. Sie verlagert die Prüflogik aber in Markdown, das vom Modell ausgeführt wird, und genau dort ist sie am unzuverlässigsten.

## Empfehlung: ein ganzzahliger CLI-Vertrag mit Docker-Fenster und striktem Guard

Der Vertrag umfasst alles, worauf sich Skills verlassen: die agentenseitigen Befehle und Optionen, die Felder des `CliJsonEnvelope`, die Felder von `data`, sowie Error- und Warning-Codes. Heute hat er keine Version, das Envelope trägt nur `ok`, `data`, `warnings` und `error` (**FACT**, [CliJsonEnvelope.cs](../src/CreativeCoders.ShadeKit.Cli/Output/CliJsonEnvelope.cs)). Die Engine bekommt in `src/CreativeCoders.ShadeKit.Core/Versions/` eine Konstante nach dem Muster von `FormatRegistry`, etwa `CliContract.Current` und `CliContract.MinSupported`, beide zum Start `1`. `version --json` meldet sie neben `formats` als `data.contract`. Der Handshake der Skills lautet dann ``Version handshake: run `shade-kit version --json --expect-contract 1`; 1 is the CLI contract this skill is written for.`` Die Engine prüft das Docker-Fenster. Ist `R > Current`, sind die Skills neuer als die Engine; die Meldung lautet sinngemäß „update the engine“. Ist `R < MinSupported`, sind die Skills zu alt; die Meldung verweist auf `shade-kit integrations install`. Dazwischen ist die Prüfung erfolgreich. Beide Fehler bekommen eigene kebab-case Error-Codes, damit Skills deterministisch reagieren. Im Bereich 50–59 sind laut `ShadeKitCliExitCodes.cs` die Codes 54–59 noch nicht belegt (**FACT** per grep, Vergabe noch offen). Die Prerelease-Nachsicht entfällt für diesen Check. Sie war nur nötig, weil Branch-Builds eine andere Produktversion tragen, und die Vertragsnummer ist auf jedem Build desselben Codes identisch.

`Current` steigt bei **jeder** für Skills sichtbaren Vertragsänderung, auch bei rein additiven. `MinSupported` steigt nur, wenn etwas entfernt oder umgedeutet wird. Der Guard sollte anfangs **strikt `R == Current`** verlangen statt nur `MinSupported ≤ R ≤ Current`. Das kostet bei einer Vertragsänderung sieben zusätzliche Zeilen. Der Grund ist der still ignorierende Parser. Ohne Kopplung könnte ein Skill eine neue Option benutzen und `R` nicht anheben. Eine ältere Engine im Fenster würde die unbekannte Option dann **still ignorieren und Exit 0 melden**, ein falsches Ergebnis ohne jedes Warnsignal. Die Literatur nennt „vergessen, das Minimum anzuheben“ als Hauptrisiko von Mindestversions-Schemata, ohne dafür ein Post-mortem zu belegen. Der strikte Guard schließt dieses Risiko mechanisch aus, und weil Release-Engine und Skills vom selben Tag stammen, verliert man nichts. Die Gegenrichtung sichert ein neuer **Snapshot-Test des Vertrags** (Vorschlag). Er erzeugt per Reflection über `[CliCommand]`, die Optionsattribute der `JsonCommandOptions`-Befehle, die `*CommandData`-Typen sowie `ShadeKitCliErrorCodes` und `ShadeKitCliWarningCodes` eine Textdatei und vergleicht sie mit einer eingecheckten Fassung, die die Vertragsnummer enthält. Ändert sich die Oberfläche ohne angehobenes `Current`, schlägt der Build fehl. Der neue Guard vergleicht nur noch Skill-Text mit einer Code-Konstante, also **ohne jede Abhängigkeit von GitVersion, Tags oder Branch**.

Die Verteilung bleibt unverändert. `IntegrationService` installiert weiter den Tag `v<engine>` und fällt auf `main` zurück. Weil der Guard im Tag-Commit `R == Current` erzwingt, installiert eine Release-Engine immer Skills innerhalb ihres Fensters. Die Endlosschleife, die der ursprüngliche Guard verhindern sollte (Exit 50 → `integrations install` holt dieselben veralteten Skills), kann so nicht entstehen ([07](../docs/feature-packages/07-claude-code-integration.md)). Neu ist, dass der Check nun auch die Pfade über die Override-Variable und über `main` echt schützt. Die Produktversion der CLI lebt weiter allein bei GitVersion. `next-version` verliert seine Skill-Rolle und kann nach dem ersten Tag ab 0.9.0 durch `+semver: minor` in Commit-Nachrichten ersetzt werden. `commit-message-incrementing` ist standardmäßig aktiv ([GitVersion 7.0 configuration](https://gitversion.net/7.0/docs/reference/configuration)). Ob GitVersion `next-version` nach einem Tag ab dieser Version tatsächlich ignoriert, ist **unverifiziert**. Die Skills verlieren `metadata.version` ganz; die Release-Nummer des Kits ist der Tag. Wer später Skills in eigenem Takt veröffentlichen will, kann auf diesem Fundament nachrüsten, ohne den Check zu ändern: Der Installer wählt dann den neuesten `skills-v*`-Tag, dessen `R` im Fenster der Engine liegt. Nötig ist das heute nicht.

Pro Ereignis sieht die Rechnung danach so aus. Ein normales Release (Engine-Fix, Skill-Textverbesserung, Formatänderung, Produkt-Minor) braucht **null** Versionsänderungen und nur den Tag. Eine neue, für Skills sichtbare CLI-Funktion braucht eine Konstante, die Freigabe des Snapshots und sieben gleichlautende Handshake-Zeilen. Die betroffenen Stellen nennt die Fehlermeldung des Guards, und ein Cake-Task zum Stempeln wäre optional. Ein Bruch des Vertrags braucht zusätzlich `MinSupported`. Heute kostet schon ein Produkt-Minor 26 Zeilen plus `GitVersion.yml`.

## Migration in einem Zug vor dem ersten installierbaren Tag

Der Zeitpunkt ist günstig. **Die Tags `v0.7.0` und `v0.8.0` enthalten kein `.claude-plugin/`. Installierbar ist erst der erste Tag mit Manifesten** (**FACT**, `git ls-tree v0.8.0`, [README.md](../docs/feature-packages/README.md)). Auch der `integrations`-Befehl kam erst nach `v0.8.0` (#34). Eine veröffentlichte Engine, die `--expect-contract` als unbekannte Option still schlucken würde, gibt es deshalb praktisch nicht. Ein Rest-Risiko bleibt bei Paketen, die zwischen den Tags aus `main` nach GitHub Packages gingen. Nach der Umstellung kennt jede Engine, die Skills installieren kann, die Option. Die harte Umstellung ohne Übergangsphase mit doppeltem `--expect` ist deshalb vertretbar.

| Schritt | Dateien | Inhalt |

## Lokales Testen: der Handshake prüft endlich auch Entwicklungsbuilds

Lokal entfällt die Prerelease-Ausnahme, weil sie nicht mehr gebraucht wird. Die Branch-Engine aus `dotnet run --project src/CreativeCoders.ShadeKit.Cli` oder ein lokal gepacktes Tool trägt die Vertragsnummer des Codes und keine Branch-Version, und der Guard hängt nicht mehr davon ab, welche Tags lokal vorhanden sind. Für Skills aus dem Arbeitsbaum bleibt der dokumentierte Weg:

```sh
SHADE_KIT_MARKETPLACE_SOURCE=$PWD dotnet run --project src/CreativeCoders.ShadeKit.Cli -- integrations install
dotnet run --project src/CreativeCoders.ShadeKit.Cli -- version --json --expect-contract 1
```

Claude Code lädt Plugins mit relativem Pfad aus einem Marketplace, der über einen lokalen Pfad hinzugefügt wurde, **an Ort und Stelle**. Änderungen wirken ab der nächsten Session oder nach `/reload-plugins`, ohne Versionsanhebung ([Claude Code plugin loading](https://code.claude.com/docs/en/plugins/loading.md)). `claude --plugin-dir .` geht ebenfalls ohne Engine. Copilot CLI lädt Plugins aus einem Verzeichnis-Marketplace seit 1.0.81 live ([Copilot CLI changelog](https://github.com/github/copilot-cli/blob/main/changelog.md)). Codex kopiert in den Cache-Ordner `local` ([Codex build plugins](https://developers.openai.com/codex/plugins/build)). Ob Codex Änderungen ohne erneutes `integrations update` übernimmt, ist **unverifiziert**.

Neu ist, dass die Prüfung zwischen Branch und Installation **echt** arbeitet. Hebt ein Branch `Current` an und ändert die Skills, während noch `main`-Skills installiert sind, meldet der Handshake korrekt „Skills zu alt“, sobald `MinSupported` steigt. Ist die Änderung nur additiv, läuft er weiter. Im umgekehrten Fall, neue Skills mit alter Engine, verlangt der Handshake ein Engine-Update. Den Ablehnungspfad testen E2E-Tests und Szenario-Fixtures mit einer beliebigen Zahl, etwa `--expect-contract 999`. Dafür braucht es keinen Release-Build und keinen Tag mehr. Unverändert bleibt ein Nebenbefund: `init` schreibt die Prerelease-Version eines Branch-Builds als `kitVersion` in `config.json` und `templates.lock.json` des Zielrepos ([RepositoryInitializer.cs](../src/CreativeCoders.ShadeKit.Core/Init/RepositoryInitializer.cs)). Das gehört in Paket 18 (`upgrade`) und nicht zu diesem Umbau.

Zwei Annahmen sollte ein Szenariolauf vor dem Umbau bestätigen. Erstens, dass alle drei Agenten den Handshake-Satz im Fließtext unverändert ausführen. Das gilt heute schon, gehört aber mit dem neuen Wortlaut erneut geprüft. Zweitens, wie Copilot und Codex den Skill-Pfad nennen, falls man die Handshake-Zeilen später über eine Datei im Plugin auf null reduzieren will. Bis das für alle drei Agenten belegt ist, bleibt die Zahl im Text die einzige verlustfreie, agentenneutrale Form.

## Fazit

Der Versionswechsel bringt vor allem eine neue Zuordnung von Zuständigkeiten. Die Produktversion beantwortet „welcher Build“ und gehört GitVersion. Die Vertragsnummer beantwortet „passt das zusammen“ und gehört den Autoren, mit einem Snapshot-Test als Gedächtnis. Die gefragte Option unabhängiger Versionen mit gegenseitigen Minima ist damit nicht verworfen, sondern auf die einzige Achse gelegt, auf der sie ohne SemVer-Prerelease-Fallen, ohne zweiten Release-Strom und ohne Umbau des Installers funktioniert. Den Ausschlag für den strikten Guard gibt ein Detail des eigenen Parsers: Weil unbekannte Optionen still ignoriert werden, wäre ein lockeres Minimum gefährlicher als gar keines.

Bemerkenswert ist, dass der heutige Lockstep beim lokalen Testen weder streng noch nützlich ist. Er blockiert den Build über den Guard und winkt die Laufzeit über die Prerelease-Ausnahme durch. Der Vertrag kehrt das um: Der Build ist unabhängig von Tags und Branch reproduzierbar, und die Laufzeitprüfung greift auf jedem Build. Weil noch kein installierbares Release existiert, ist der Umbau jetzt am billigsten. Nach dem ersten Tag mit Manifesten bräuchte er eine Übergangsphase mit doppeltem Handshake.
