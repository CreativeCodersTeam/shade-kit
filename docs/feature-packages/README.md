Status: draft, 2026-10-14, updated 2026-10-18 (consistency review, findings clarification, and implementation of package 02), 2026-10-21 (implementation of package 03, its code review rework, and the rework after its second code review), 2026-10-22 (code review verification of package 03), 2026-10-23/24 (rework of file content handling), 2026-10-24 (documentation check against the code), 2026-10-25 (rework of `feature new` and its code review), 2026-10-26 (implementation of package 04), 2026-10-27 (documentation check after package 04), 2026-11-01 (implementation of package 05), 2026-11-04 (split of package 06 into the sub-features 06-1 to 06-9), 2026-11-06 (implementation of package 06-1 and its code review, and implementation of package 06-2), and 2026-11-08 (implementation of package 06-3, and implementation of package 06-4 and its code review rework). Parts that exist in the code are labelled **Implemented**.

Each package describes the functional behaviour of one clearly bounded piece of v1, with its benefit, scope, acceptance criteria (`FPnn-ACm`), and open points. The number prefix is the implementation order: every package depends only on packages with a lower number.

Labels follow the concept: **Decided** (confirmed in the concept interview or a later interview or review named with its date), **Proposed** (added in the concept or in these packages, not confirmed yet), **Open**, **Unverified**, **Implemented** (exists in the code; the label names where).

New open points from the packages:

- Trackers beyond GitHub in the id scheme, and readers for trackers that `gh` cannot read: every host in `trackers` is read with `gh` in v1 (03).
- Changing the profile of an existing feature (04).
- The `report` setting in the result of `phase start finish`, which the `shade-kit-finish` skeleton expects (04, owned by 15).
- History timestamps `at` with fractional seconds, while `createdAt` has whole seconds (04).
- Skill skeletons not yet aligned with the built `phase` commands (04, 05, 06): 13 skeletons still say in their source comment that every command other than `version`, `init`, and `feature …` is planned; `shade-kit-finish` expects the `report` setting in the result of `phase start finish`; no phase skill and not `shade-kit-next-phase` says to show the `warnings` of `phase start` and `phase next` (`gates-defaults-used`, `gate-entry-ignored`); the refusal table of 06 has no row for exit code 47 (`checklist-template-not-found`) and none for 17 (`kit-file-write-failed`, since 2026-11-04). (`shade-kit-next-phase` now says that only `pending` and `forward` have a gate, 2026-10-30.) Assigned on 2026-11-04: the rows for 17 and 47, a fallback row, and the warnings to 06-3; the skeletons to 06-9; the `report` setting to 15.
- Skill version (06-2, 2026-11-04): every skill carries its kit version hardcoded in its frontmatter (`metadata.version`), initial value `0.7.0` (2026-11-06); its alignment with the GitVersion version and the release tag is skipped for now, which breaks the rule in `GitVersion.yml` that no version is maintained by hand (06-2, 07, 19). Claude Code does not show the frontmatter to the model (checked on 2026-11-06 with Claude Code 2.1.318 on project-level skills, 06-2), so the handshake step states the version in its text. **Unverified:** whether Copilot and Codex show the frontmatter to the model (08).
- Phase skills are restricted to user invocation only by convention (06-2, 08): a technical restriction such as Claude Code's `disable-model-invocation` is a possible later addition; whether Copilot and Codex offer one is part of the research of 08.
- Skill reactions to a refused start, the refusal table of the next-steps message, and the active-feature check of `new` are **Proposed** (06-3, 09). The next-steps skill is built (06-3, 2026-11-08); its defaults are also **Proposed**: the table is keyed by error code, a failing `phase next` goes through the table, repeated warnings are shown once, and a refusal ends with calling the skill again. Rows 20–22 and 47 name `shade-kit upgrade`, which comes only with package 18.
- Defaults of the 04 implementation that the user has not confirmed yet (**Proposed** in 04): the repeated gate of a pending forward transition, approving a pending reopen of a phase that can no longer be reopened, the conditions for a `feature.json` without `currentPhase`, the done rule, the override deletion of `phase complete`, the plain-text wording, and `null` parts of `phase next`.
- Value and unit of the coverage threshold `coverageThreshold` in `config.json` (05, 14).
- Follow-ups from the implementation of 05 (2026-11-01): `checklist` values with control characters or `:` (a Windows alternate data stream) are not rejected; the order of `gate-entry-ignored` warnings relies on `Dictionary` enumeration order, which .NET does not guarantee; the cached `GatesConfig` is one shared mutable object; a file at `features/<id>/checks` ends `phase start` with exit code 255 (resolved on 2026-11-04: exit code 17, since the /simplify review of feature/feature-05 for every refused write in `.shadekit/`, 01); two concurrent starts could race between the existence check and the write of the copy; repositories initialised before 2026-11-01 get the built-in gate defaults with a warning until an upgrade (18) writes `profiles` (05).
- Supported way to install a Claude Code plugin at user level from a CLI (07, **Unverified**).
- Follow-ups from the implementation of 02: plain output wrapped at 80 columns when stdout is not a terminal, skeleton templates that name their owner package, a second `.gitignore` comment line when only an entry is missing (02). From its code review: a dangling symbolic link ends with a host error and a read-only target file fails only after `.shadekit/` is written (02).
- Follow-ups of 03 after its code review rework and second code review (2026-10-21): the process run of `GitCommandRunner` (output capture, exit codes, kill) is not covered by tests, and its read tasks are not observed after a kill (F03, accepted); a FIFO as `--source` blocks `feature new`; `drop` can delete an override that was changed to another feature between its check and the delete; on some systems the rename of `new` or `drop` can replace an empty folder created at the wrong moment; a file at `features/<id>` makes `feature new` end with exit code 255; a rename that fails only for a moment (for example on Windows while a virus scanner holds new files) is not retried and ends with exit code 35; unknown extra arguments are ignored silently; `git.cmd` shims are not found (no `PATHEXT`). Accepted as is by the user from the second code review: bidi format characters and U+2028/U+2029 pass the title check (N03); 03 says that a canceled `init` rolls back what it created, but it removes only `.shadekit/` (N04); Ctrl+Break and SIGQUIT also cancel with exit code 130 (N05); the `invalid-title` hint "Pass such a title with --title." is circular for a title from `--title` (N06); a theory in `ConsoleCancellationTests` branches in its Arrange section (N07).
- Follow-ups of 03 after the code review of the rework of `feature new` (2026-10-25): accepted as is by the user, a second `AddShadeKitCore()` call registers the configuration of the named HTTP client twice, so that client would send the `User-Agent` product twice (F3, **Unverified** at runtime; the CLI calls it once).
