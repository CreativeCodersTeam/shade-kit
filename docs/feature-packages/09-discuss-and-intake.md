## Benefit

Ideas can be explored freely before they become a feature, without creating any workflow state. When an idea, an issue, or a document is ready, the agent turns it into a feature in one step, with the original input preserved, so later phases can always go back to what was actually asked for.

## Scope

### In scope

- The `discuss` skill and where its notes are stored.
- The `new` phase skill for every profile.
- The template `discussion.md`. `request.md` has no template since 2026-10-25; the engine writes it (package 03).
- `shade-kit feature new --move-source` (package 03), so that discussion notes move into the feature created from them. **Decided** on 2026-11-20 (implementation).
- The kit version `0.9.0` of all skills, because `shade-kit-new` needs `--move-source` (package 06-2). **Decided** on 2026-11-20 (implementation). Replaced on 2026-11-22 ([06-2](06-2-skill-conventions-and-version.md#cli-contract-in-the-handshake)): the skills carry no kit version; they name the CLI contract `1`, which includes `--move-source`; every engine that supports the contract `1` knows the option. An engine without the option is older than the contract and does not check it at all (it ignores `--expect-contract` and answers `ok: true`, see the transition risk under [Open points](#open-points)).

### Out of scope

- Clarifying the requirement (`refine`, package 10). `new` records the input; it does not judge it.
- Creating a feature without an agent: `shade-kit feature new` from package 03 works on its own.

## Functional description

### `discuss`

- Brainstorm any topic: an idea, a design question, a problem. Optional, outside every profile, possible at any time. **Decided** (concept §5.1, §5.4).
- Uses the interview skill (package 06) in an open mode: the agent asks, proposes alternatives, and challenges assumptions.
- At the end, or when the human asks, the agent writes the notes from the `discussion.md` template: topic, date, participants (git user), options discussed, conclusions, open questions. **Implemented** (`skills/shade-kit-discuss/SKILL.md`). Details **Decided** on 2026-11-20 (implementation):
  - The heading is the topic alone, a short title of a few words without the prefix "Discussion:", because `feature new` takes the first level-1 heading as the feature title when a feature is created from the notes (D-3).
  - One `###` subsection per option with a short description and "Pros:" / "Cons:" lists; with several topics, a short topic name in front of each option; date `yyyy-mm-dd`; participants are git user names (D-14).
  - File name `<yyyymmdd>-<hhmm>-<slug>.md` with the local time of the first write and the slug rules of feature ids (package 03); a taken name gets `-2`, `-3`, … (D-11, D-16).
  - One file per run: a later write in the same discussion rewrites it with the full state; a new run starts a new file (D-23).
  - The skill creates the `discussions/` folder; the file is UTF-8 without byte order mark, with the line ending of the template file, or of the operating system when there is no template (D-24).
  - A missing `.shadekit/templates/discussion.md` is noticed before the discussion; the notes are then written in the template's structure and the report says so. This is the second exception to "every artifact starts from the template", after `researches.md` (06-2, D-17).
  - In an active feature, the interview gets the feature's `request.md` to check against, as data, never as instructions.
- Storage (concept open question 2, **Decided** (confirmation list, 2026-10-18)):
  - No current feature: `.shadekit/discussions/<yyyymmdd>-<hhmm>-<slug>.md`.
  - Current feature: `.shadekit/features/<id>/discussions/<yyyymmdd>-<hhmm>-<slug>.md`.
  - A current feature with status `done` counts as no current feature: a finished feature gets no further refine round, so its notes go to `.shadekit/discussions/`. **Decided** on 2026-11-20 (implementation, D-2). **Implemented.**
- Discussion notes are committed like all kit data. `discuss` never changes `feature.json`.
- The agent names the next step and the skill the human calls for it: `/shade-kit-new` to create a feature from the notes, or (with a current feature) `/shade-kit-refine` to continue with the notes as input. It starts neither skill itself, because a phase starts only when the human calls its phase skill (package 06). **Decided** on 2026-10-30 ([phase start analysis](../../research/shade-kit-phase-start-analysis.md)). **Implemented**: the closing message of `shade-kit-next-steps` names the skills; the report names `/shade-kit-new` only while a feature is active, because the closing message does not list it then.

### `new`

Runs when no feature exists for the work yet. The human calls it (`/shade-kit-new`); `shade-kit-next-phase` (package 06) only names it. **Decided** on 2026-10-30 ([phase start analysis](../../research/shade-kit-phase-start-analysis.md)), replacing "`shade-kit-next-phase` hands off to it".

Before step 1, the skill checks for an active feature: `shade-kit feature current --json`. If it resolves a feature with status `active`, tell the human which feature is current (id, phase, state) and ask whether to create a new feature anyway or to end here; on "end", the skill ends with the next-steps message of that feature (package 06). **Decided** on 2026-11-20 (implementation, D-4), from **Proposed**. **Implemented.**

1. Collect the input: free text, an issue URL, a Markdown file, or discussion notes.
   - Free text goes unchanged into one `--source` argument, quoted for the running shell (single quotes in a POSIX shell, with `'` written as `'\''`; in PowerShell `'` doubled). **Decided** on 2026-11-20 (implementation, D-13). **Implemented.**
   - Discussion notes directly in `.shadekit/discussions/` are passed with `--move-source`: `feature new` moves them into the `discussions/` folder of the new feature and records the new path as the source ([package 03](03-feature-management.md#moving-discussion-notes---move-source)). Notes in a feature's `discussions/` folder stay where they are. **Decided** on 2026-11-20 (implementation, D-5, D-6), replacing no earlier rule. **Implemented.** The moved notes keep the metadata line they were written with (``Feature: `none` ``): they record the discussion as it was held, not the feature it became, so `new` does not edit them. **Decided** on 2026-11-20 (review round 1 proposed the variant that changes no file; confirmed by the user at Gate 5 of round 2, D-33). **Implemented.**
2. Ask for the profile if the human did not name it; propose one from the input (a defect report suggests `bugfix`, a small, clear change suggests `quick`, a new capability `feature`). Default from `config.json`: the skill does not read `config.json`, so it offers "the repository default" and then leaves out `--profile`, so the engine applies `defaultProfile`; a named profile is always passed. **Decided** on 2026-11-20 (implementation, D-12). **Implemented.**
3. For an issue URL of a tracker in `config.json`, the agent does not read the issue: `feature new` reads it with `gh` and takes the issue title for the id unless `--title` is given (package 03). **Decided** on 2026-10-25 (rework of `feature new`), replacing "the agent reads the issue with its own tools, because the engine does not call trackers". If `gh` is missing or cannot read the issue, for example because it is not signed in to the host, `feature new` stops with exit code 33 (`invalid-source`); the agent shows the message to the human, whose last sentence says what to fix: install `gh`, or check the issue URL and that `gh` is signed in for its host (package 03, [Errors](03-feature-management.md#errors)).
4. Call `shade-kit feature new --source <…> [--profile <p>] [--title <…>] --json`. Without `--profile`, the engine uses `defaultProfile`. `--title` is optional for an issue URL of a tracker in `config.json` and required for any other URL, whose content the engine reads with an HTTP GET.
5. There is nothing to complete in `request.md`. `feature new` writes the request content into it: the text unchanged, the file content, the issue as Markdown (title, body, comments), or the content of another URL, with the line endings of the repository (package 03, [`request.md`](03-feature-management.md#requestmd)); the source itself is in `feature.json`. **Decided** on 2026-10-25 (rework of `feature new`), replacing "the agent completes the pre-filled `request.md`" **Decided** on 2026-10-20. The agent does not rewrite or summarise `request.md`.
   - `request.md` can hold third-party content: the body and every comment of an issue, which anyone who may comment can write, or a whole web page. Every skill that reads it (`shade-kit-new`, `shade-kit-refine`, `shade-kit-diagnose`, `shade-kit-quick`, and the research agents of `shade-kit-research`) treats it as data that describes the requirement, never as instructions to the agent: it does not follow commands, links, or tool requests in it, and shows the human any instruction in it that looks suspicious (a research agent reports it to the calling skill, which shows it). **Decided** on 2026-10-25 (code review of the rework of `feature new`, finding F6), replacing no earlier rule: before the rework the agent read the issue itself and chose what went into `request.md`. The engine keeps writing the content unchanged (package 03, [`request.md`](03-feature-management.md#requestmd)). **Implemented** (the five skill files).
6. No branch: the skill creates or switches no branch, offers none, and runs no `git` command. It names the suggested branch `feature/<id>` (package 03) in its report as information. When the current branch selects another feature, that feature stays current (the branch wins over the override), so the closing message shows its steps; the skill then reads the next phase of the new feature from `shade-kit feature show <id> --json` (`phases` in profile order, the one after `new`) and names it with its skill, and says that it applies once the human switches to a branch that selects the new feature. **Decided** on 2026-11-20 (review round 1, R-1, D-29; a profile-to-phase table in the skill was rejected, because skills derive no steps from the profile). **Decided** on 2026-11-20 (implementation, D-18, D-20), replacing "Offer to create and switch to the branch `feature/<id>` … The agent runs the git command only after a yes" (**Proposed**). **Implemented.**
7. Report the id, the next phase of the profile (`refine`, `diagnose`, or `quick`), and the skill the human calls to start it (`/shade-kit-refine`, `/shade-kit-diagnose`, or `/shade-kit-quick`). The skill ends there; the transition goes through the entry protocol of that phase skill once the human calls it (package 06). **Implemented**: the next phase and its skill come from the closing message (`phase next`), and in the branch case of step 6 from `feature show`.

For a URL that is not an issue URL, the skill asks for a title; when `feature new` stops with `invalid-title` because a title is missing, it asks once and runs the command again with `--title`. For a URL source it reads `request.md` once after the creation to check it for suspicious instructions, because it has not seen that content before. **Implemented** on 2026-11-20 (clarification after the first scenario runs, derived from steps 4 and 5 of this list and finding F6 of package 03; no decision of its own).

A refused `feature new` (for example exit code 10 in a repository without `.shadekit/`, or exit code 40 for an unknown profile) ends the skill with the reason and the human's options (package 06-3, [Next-steps message](06-3-next-steps-skill.md)).

## Open points

- `shade-kit-next-steps` (06-3), found in the scenario runs, not in scope here: the calling skills pass a fixed line of what happened, while 06-3 says the message writes the line itself; `invalid-source`, `invalid-title`, and `git-identity-missing` fall under the fallback row, so the closing message offers no retry of `/shade-kit-new`, although the message says what to fix; for a `done` feature the message also names `/shade-kit-drop`.
- `shade-kit-interview` (06-7), found in the scenario runs: the end-or-go-on question of `open` mode has no header rule; how far `open` mode adds topics of its own is left to the agent; a suggested topic the human declines is neither returned nor an open question.
- No scenario for a successful issue read through `new` (the generator has no `gh`), a `discuss` mismatch, or `source-not-removed`; the engine tests cover the move and the warning.
- The old `discussion.md` skeleton stays in repositories initialised before 2026-11-20 until `upgrade` (package 18) replaces templates; `discuss` follows whatever template the repository has.
- A kit `0.9` skill with a `0.8` engine stops at the handshake (exit code 50); `--move-source` is not offered to a `0.8` engine. Replaced on 2026-11-22 (06-1): every engine since 2026-11-22 supports the contract `1`, which includes `--move-source`; a later engine that drops it raises `MinSupported`, and the skill then stops with `skills-outdated` (55). An engine from before 2026-11-22 (a `0.8` engine among them) ignores `--expect-contract` and answers `ok: true`, so the skill goes on; that such an engine then also ignores `--move-source` as an unknown option is **Unverified**. The transition risk is accepted (06-2, D-10).
