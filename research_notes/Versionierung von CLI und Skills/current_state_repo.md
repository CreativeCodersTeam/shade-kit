## 1. Where is the version defined, computed, embedded, and checked?

### Takeaway
There is exactly one computed version (GitVersion from git history + `next-version`), embedded as the assembly informational version and read at runtime by `EngineVersionProvider`; it is used for the `--expect` handshake (major.minor match, prerelease only warns), for the marketplace ref (`v<engine>` / `main`), for `init` (`kitVersion` written into `.shadekit/`), for the HTTP User-Agent, and by the Cake smoke test. The skills carry a second, hand-maintained copy (`metadata.version` + handshake text) that a guard test ties to the GitVersion major.minor.

## 5. Concrete local-testing scenarios and pain points; documented rationale for lockstep

### Takeaway
Lockstep was chosen so that "the tag that builds the engine also names the tree the agent installs", which makes a release self-consistent without any engine-side record. The costs fall on development: a minor raise is a 20-file atomic edit coupled to GitVersion; prerelease engines disable the check; local skill testing needs the env override and loses all version reporting; `init` leaks prerelease versions into a repository's `.shadekit/`.

### Cited Findings
**Documented rationale**
- FACT: concept §9.6: "Plugin content and CLI share one version number. A skill checks `shade-kit version` before it runs." Content packing was replaced 2026-11-13 by "an engine installs the tree of its own tag `v<version>`" — [research/shade-kit-concept.md §9.6 (lines ~354-358)](research/shade-kit-concept.md).
- FACT: 07: no `version` in `plugin.json` "so no second version is kept by hand"; "Plugin and CLI release together … now holds through the tag" — [07:41,44](docs/feature-packages/07-claude-code-integration.md). 19: "every release delivers engine and agent content with the same version number, so the version handshake works out of the box" — [19:14,45](docs/feature-packages/19-release-and-distribution.md).
- FACT: the guard exists because of a review Major: a release engine installs the skills of its own tag; if they carry another major.minor every handshake fails with 50 and the hint `integrations install` installs the same stale skills again (loop) — [07:240](docs/feature-packages/07-claude-code-integration.md), [README.md:187](docs/feature-packages/README.md).
- FACT: acknowledged open points: the hand-raise "still breaks the rule in `GitVersion.yml` that no version is maintained by hand"; writing the version from GitVersion (e.g. a Cake task, package 19) and a pre-tag check in `verify-tag` are open/not selected — [06-2:98](docs/feature-packages/06-2-skill-conventions-and-version.md), [19:66](docs/feature-packages/19-release-and-distribution.md). "The value is raised by hand for every release whose major or minor differs" — [06-2:100](docs/feature-packages/06-2-skill-conventions-and-version.md).
- FACT: proposed rule: a format version change is at least a minor release "so the handshake rule … catches it" (**Proposed**) — [19:46](docs/feature-packages/19-release-and-distribution.md).

## 6. Does the CLI expose a protocol/contract version or capability list usable as a compatibility contract?

### Takeaway
No explicit CLI contract version or capability list exists. The closest existing precedents are the `formats` map in `version --json` (integer format version per file type, with a `minEngineVersion` table) and the stable `error.code`/warning-code vocabulary; the JSON envelope itself is unversioned.

### Cited Findings
- FACT: `CliJsonEnvelope` has exactly `ok`, `data`, `warnings`, `error` — no version field — [src/CreativeCoders.ShadeKit.Cli/Output/CliJsonEnvelope.cs:27-48](src/CreativeCoders.ShadeKit.Cli/Output/CliJsonEnvelope.cs).
- FACT: `version --json` `data.formats` lists format id → `CurrentVersion` from `IFormatRegistry` — [VersionCommand.cs:126](src/CreativeCoders.ShadeKit.Cli/Commands/Version/VersionCommand.cs); output observed `{config:1,gates:1,feature:1,current-feature:1,templates-lock:1}` (run).
- FACT: format versioning model: integer `schemaVersion` per file, a migration chain per type, `minEngineVersion` stamped on every write, "The format version changes only when the structure changes, not with every engine release" — [research/shade-kit-concept.md §9.1](research/shade-kit-concept.md); `FormatDefinition(id, minEngineVersions)` [src/CreativeCoders.ShadeKit.Core/Formats/FormatDefinition.cs:33-39](src/CreativeCoders.ShadeKit.Core/Formats/FormatDefinition.cs); `FormatTooNewException` → "requires shade-kit >= {MinEngineVersion}" [CliErrorMapper.cs:852-855](src/CreativeCoders.ShadeKit.Cli/Output/CliErrorMapper.cs).
- FACT: skills react to `error.code`, not exit codes; every exit code has a kebab-case error code; warnings have codes — [CLAUDE.md Agent contract](CLAUDE.md).
- FACT: the 2026-11-04 split log noted that the handshake "had no source for the skill's own kit version (… no plugin manifest, `version --json` returns only `engineVersion` and `formats`)" — [README.md:174](docs/feature-packages/README.md).

### Inferences
- The format-version design (integer, raised only on structural change, min-engine table, migration) is a ready in-repo template for a CLI contract version: e.g. `data.contract: { version: N, minSupported: M }` next to `formats`, checked by `--expect-contract N`.
- Unknown options are silently ignored by the parser (`--expect=1.2.3` is ignored, exit 0) — [06-1:40](docs/feature-packages/06-1-engine-version-check.md); so a skill cannot probe a capability by just calling an option; an explicit capability/contract declaration is needed.

### Gaps
- No capability list was found anywhere (`git grep -i capabilit` not run exhaustively; the `version` data model shows none — FACT for `VersionCommandData`).

## 7. Change map per candidate scheme

### Takeaway
(a) is the smallest change but keeps all coupling; (b) is limited by the no-frontmatter/no-transformation constraints and by Claude Code's SHA-based plugin versioning; (c) and (d) decouple the release streams and remove the GitVersion dependency of the guard, at the cost of touching the checker, the version envelope, skills, guard, integrations ref logic (c only), and many docs.

### Cited Findings (the files involved — all verified to exist and to hold the named logic, see §1–§6)
**(a) Keep lockstep, automate the bump** (script/Cake task rewrites frontmatter + handshake texts from GitVersion `MajorMinorPatch`, or from `next-version`)
- New: `build/Tasks/<BumpKitVersion>Task.cs` (+ registration in [build/Program.cs](build/Program.cs)), or a script; optionally a check task in `verify-tag` of [.github/workflows/release.yml:24-36](.github/workflows/release.yml) (open point in [19:66](docs/feature-packages/19-release-and-distribution.md)).
- Rewritten by the tool (still committed, because the plugin is installed from the git tree and there is no install-time transformation, [08:49](docs/feature-packages/08-copilot-and-codex-integration.md)): 19 × `skills/*/SKILL.md:5`, 5 handshake lines, 2 command-list lines (§3); `GitVersion.yml:15`.
- Unchanged: `SkillKitVersionTests` (stays as safety net), engine code. Docs: 06-2 (open point "writing the version from GitVersion" [06-2:98](docs/feature-packages/06-2-skill-conventions-and-version.md)), 19, CLAUDE.md skill conventions.
- Inference: does not solve local testing (prerelease = no check; branch installs `main`), nor the skill→engine patch dependency, nor parallel-branch conflicts; only removes typing.

**(b) Skills read the version from a generated/bundled file**
- Constraint facts: the model does not see frontmatter (§3); Claude Code gives the skill "Base directory for this skill: <dir>" [06-2:71](docs/feature-packages/06-2-skill-conventions-and-version.md) (Copilot/Codex equivalent **Unverified**); a root `plugin.json`/`marketplace.json` or agent-specific manifest is forbidden by [SingleSkillSourceGuard.cs:62-68](tests/CreativeCoders.ShadeKit.Core.Tests/Skills/SingleSkillSourceGuard.cs); adding `version` to `.claude-plugin/plugin.json` would replace the commit-SHA plugin version [07:41](docs/feature-packages/07-claude-code-integration.md) (Inference: Claude Code would then only see an update when the version changes — **Unverified** behaviour).
- Variant b1 (skill reads file, passes value): touches 5 handshake steps + 2 command lists (add a read step, agent-specific text per [CLAUDE.md one-source rule](CLAUDE.md)), `SkillKitVersionTests` (check file instead of frontmatter/text), `SkillAgentWordingTests` possibly, `tests/skill-scenarios/generate_fixtures.py:38,107-116` and `checks/check_runs.py:223-224`, 06-2, 06-5, 06-6, 06-9, CLAUDE.md.
- Variant b2 (engine reads it: e.g. `shade-kit version --json --skill-dir <base dir>` parses `metadata.version` from the installed `SKILL.md`): touches `VersionCommandOptions`, `VersionCommand`, `EngineVersionChecker` (or new reader), `CliErrorMapper`, new exit/error codes in `ShadeKitCliExitCodes`/`ShadeKitCliErrorCodes`, end-to-end tests in `tests/CreativeCoders.ShadeKit.Cli.Tests/Commands/Version/`, the 5 handshakes. Still needs the file to be written/committed (≥1 place), so only the count drops.
- Inference: b reduces the edit count but not the coupling; it adds an agent-dependent step (base dir), which the "agent-agnostic without loss" rule in CLAUDE.md must justify.

**(c) Independent versions with minimum-version expectations each way** (skills declare `minEngine`, engine declares `minSkills`/supported kit range)

- Skills/guards: 19 frontmatters (+ new `metadata.minEngine`?), 5 handshakes + 2 lists, `shade-kit-next-steps/SKILL.md:95` (refusal text), `SkillKitVersionTests` (rewrite: min engine ≤ build version instead of major.minor equality), `tests/skill-scenarios/*`.

**(d) Separate contract/protocol version** (integer, raised only on breaking CLI/JSON-contract change; product versions stay GitVersion)
- Engine: new constant/registry (pattern: `FormatRegistry`/`FormatDefinition`), `VersionCommandData.cs` (add e.g. `contract` next to `formats`), `VersionCommandOptions.cs` (e.g. `--expect-contract <n>` or reuse `--expect` with a new grammar), a checker in `Versions/` (or rewrite `EngineVersionChecker`), `CliErrorMapper` messages, `ShadeKitCliExitCodes`/`ErrorCodes`/`WarningCodes` (50 semantics), tests as in (c).
- Skills: 5 handshakes + 2 lists (one integer instead of SemVer), frontmatter (`metadata.version` kept for humans or replaced by `metadata.contract`), `shade-kit-next-steps/SKILL.md:95`; `SkillKitVersionTests` → compares against the engine's contract constant (pure code, no GitVersion), which removes the build-version dependency of the guard; `tests/skill-scenarios/generate_fixtures.py`, `check_runs.py`.
- Versioning/CI: `GitVersion.yml:6-15` (`next-version` and its comment no longer needed for skills), nothing mandatory in `release.yml`; integrations can keep `v<engine>` pinning (`IntegrationService.cs:265-290` unchanged) since the tag tree still holds the skills the engine was built with; the contract check then protects the override/`main` paths too.
- Docs: 06-1, 06-2, 07 (Kit version guard, FP07-AC2 wording "same kit version"), 08, 19 (Version section, "format change ⇒ minor" proposal), concept §9.6, CLAUDE.md.

### Inferences
- (d) is the only scheme that (1) needs no GitVersion coupling in the guard, (2) keeps the handshake meaningful on prerelease/local builds (contract number is identical on every build of the same code), and (3) can reuse the in-repo `formats` precedent. It still needs a rule for who raises the contract number (engine authors, when a skill-visible command/JSON/error code changes) — which is a review discipline, not something GitVersion computes.
- (c) is the most invasive because the marketplace ref derivation (`v<engine>`) is built on lockstep; a hybrid "(d) for compatibility + keep `v<engine>` tag pinning for distribution" touches far fewer integration files.
- Whatever the scheme, FP07-AC2 ("installed skills have the same kit version as the engine that installed them", [07:254](docs/feature-packages/07-claude-code-integration.md)) and FP19-AC3 ([19:59](docs/feature-packages/19-release-and-distribution.md)) are acceptance criteria phrased in lockstep terms and would need rewording for (b)-(d).
